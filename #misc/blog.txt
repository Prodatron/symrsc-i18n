Multilingual support in SymbOS

Over the past few days I've finally completed 95% of the multilingual support in SymbOS. At the beginning this was just meant to be a small gimmick for the long filenames in SymbOSVM and Japanese translations for MSX users. However, it ended into a larger project that took much more time than I expected. But as usual - once you start something, you want to have it as complete as possible.


In total, four different steps had to be done:


1.) Support for the full 255 Characters

This has been described earlier. Due to memory limitations, the system font in SymbOS was previously limited to 96 characters. Now, with the option to move the font to additional memory, 255 characters are possible on every platform.


2.) Operating System and Applications become Multilingual

Texts in apps and in the operating system itself are now interchangeable. If a string starts with the byte 1, it is followed by a 16-bit pointer to the actual text, which can be located elsewhere. This works for all kind of strings addressed by any GUI controls. It allows for the implementation of pointer lists followed by the actual texts. After launching, an app can call a new OS function that loads the selected language from a "*.LNG" file. The default English texts are overwritten with the language-specific texts, and the pointer list is adjusted, as expressions vary in length depending on the language. Modifying an existing app for this is surprisingly easy because, in SymbOS, all texts must be located in the so-called "Data Area" anyway. They are therefore usually already grouped and not scattered over the whole source code. A Python script is used to create CSV files containing one column for the text ID and one for the English expression. A translator simply adds further columns for the new languages, and the Python script automatically generates a compressed LNG file that can contain any number of translations for an app or app group. Languages are identified by unique IDs (ISO-639 and MS-LCID).


3.) Platform-Independent Keyboard Mapping for International Layouts

SymbOS now runs on 8 different platforms. How do you map any number of keyboard layouts to all these platforms? If we had, for example, 5 different languages, this could result in 8 x 5 = 40 maps - too much work and too many config files. Instead, there is now one mapping per platform for the standard US-ISO layout with 47 character keys, which provides access to the 94 ASCII characters 33-126 (optionally one or two more keys for ANSI or Portuguese keyboards). This means that keyboards on any platform return unique characters, which can now be converted into the country-specific layout with a single additional map.

Most layouts require "AltGr" as an additional switch besides "Normal" and "Shift", allowing up to 4 layers just for character input (not to be confused with the "Control" and "Alt" layers!). On the CPC, the small "Enter" key is now used for this. At least on the 6128 it has the correct position (the "Copy" key already works as the "Alt" key), while other platforms use similarly positioned special keys for this purpose.


4.) Romaji Input and Deadkey Support via Prefix Trees

While it's possible to directly access Hiragana and Katakana characters on Japanese keyboards, Japanese users likely prefer to type their text using "Romaji input" mode. Hiragana and Katakana ("Kana") are syllabic scripts, meaning each character typically represents a consonant and a vowel (e.g., KA, KI, KU, KE, KO, SA, SI, SU, SE, SO, etc.). Simply type the two or three Latin characters that describe such a syllable, and you'll receive a Kana character. Depending on whether Shift or Caps Lock is active, either a Hiragana or a Katakana character will appear. A complete translation table for this can be found here (scroll down to the bottom):

https://msxjpn.jimdofree.com/%E3%81%8B%E3%81%AA-%E6%97%A5%E6%9C%AC%E8%AA%9E%E5%85%A5%E5%8A%9B/

Since the latin-kana mapping is explicit, it can be implemented using a prefix tree ("trie") with up to 52 branches per node.

For Latin layouts, however, so-called dead keys are needed, which create letters composed of two characters. Pressing the first character does nothing; pressing the second character produces the actual letter. E.g. ` and E produce È, ^ and A produce Â etc. This is necessary for letters with diacritics that are not directly assigned to a key. Here we can also use our new prefix trees, one for each country-specific keyboard layout.


In SymbOS, new optional operating system features are, wherever possible, outsourced to "Daemons" to keep the core system small and still executable on minimal systems. This is the same for the new multilingual support, which requires very little new code on the OS core side. Most of the code and data for the new features have been placed inside the loadable "Extended Desktop" module, which now also works as a language/"i18n" daemon.

What's still needed are intensive tests, and on the MSX the output of alternative character sets needs to be sped up. The OS, all system applications, and important standard apps have already been translated into German, Japanese (thanks to Hando!), and Dutch (thanks to @EdoZ!).

Of course, French, Spanish, Greek, Turkish, Italian and other translations would be cool too. @prevtenet is even thinking about a translation for Cherokee, he already did the font, and the keyboard definition as there well. The same is prepared for Greek and Turkish.

Any help is very welcome, if you're interested, just write!

In den letzten paar Tagen habe ich endlich die Multilingual-Unterstützung in SymbOS fertiggestellt. Zuerst sollte das nur ein kleines Gimmick werden für die langen Dateinamen in SymbOSVM und japanischer Übersetzung für MSX User. Dann aber hat es sich zu einem größeren Projekt entwickelt, das viel mehr Zeit in Anspruch genommen hat, als ich erwartet hatte. Wenn man einmal gewisse Sachen angefangen hat, möchte man sie am Ende ja doch so vollständig wie möglich haben.

Insgesamt mußten vier verschiedene Schritte unternommen werden:

1.) Optionale Unterstützung für volle 255 Zeichen

Das hatte ich weiter oben schon beschrieben. Aus Speicherplatzgründen war der Systemfont in SymbOS bisher nur 96 Zeichen groß. Jetzt können unter optionaler Auslagerung des Fonts auf erweiterten Speicher auf jeder Plattform 255 Zeichen angeboten werden.

2.) Betriebssystem und Apps werden Multilingual

Die Texte in Apps und auch im Betriebssystem selbst sind nun austauschbar. Startet ein String mit dem Byte 1, dann kommt danach erstmal ein 16bit Zeiger auf den eigentlichen Text, der ganz woanders stehen kann. Damit können Zeigerlisten realisiert werden, gefolgt von den eigentlichen Texten. Eine App kann nach dem Starten eine neue Funktion aufrufen, die aus einer "*.LNG"-Datei die gewünschte Sprache nachlädt. Die englischen Default-Texte werden mit den sprachspezifischen Texten überschrieben, und die Zeigerliste wird anhand der neuen Texte angepasst, denn in jeder Sprache sind Ausdrücke unterschiedlich lang. Bestehende Apps hierfür vorzubereiten geht erstaunlich einfach, weil Texte in SymbOS sowieso alle in der sogenannten Data-Area stehen müssen. Sie sind also meistens schon zusammengefasst und nicht über den gesamten Sourcecode verstreut. Mittels Python-Scripte werden daraus CSV-Dateien erstellt, die eine Spalte für die Text-ID und eine für den englischen Text enthalten. Ein Übersetzer fügt nun einfach weitere Spalten hinzu mit den neuen Sprachen, und ein anderes Python-Script generiert daraus automatisch eine komprimierte LNG-Datei, die beliebig viele Übersetzungen für eine App bzw. App-Gruppe enthalten kann. Sprachen werden über eindeutige IDs (ISO-639 und MS-LCID) identifiziert.

3.) Plattform-unabhängiges Tastatur-Mapping für internationale Layouts

SymbOS läuft mittlerweile auf 8 verschiedenen Plattformen. Wie mappt man beliebig viele Tastaturlayouts auf all diese Plattformen? Hätten wir z.B. 5 verschiedene Sprachen, könnten sich darauf 8 x 5 = 40 Mappings ergeben, ein riesiger Aufwand. Statt dessen gibt es pro Plattform jetzt ein Mapping für das Standard US-ISO Layout mit 47 Zeichentasten, mit dem die 94 ASCII-Zeichen 33-126 erreicht werden (optional zwei oder vier mehr für ANSI- bzw. portugisische Tastaturen). Somit geben die Tastaturen beliebiger Plattformen eindeutige Zeichen zurück, die nun mit einer einzigen weiteren Map in das länderspezifische Layout umgewandelt werden können. Die meisten Layouts benötigen neben Normal und Shift noch AltGr als weiteren Umschalter, was bis zu 4 Layer nur für die Zeicheneingabe ermöglicht (nicht zu verwechseln mit Control und Alt). Auf dem CPC dient hierfür nun die kleine Enter-Taste. So hat man zumindest auf dem 6128 die korrekte Position (die Copy-Taste bildet ja bereits die Alt-Taste ab), auf anderen Plattformen werden ähnlich platzierte Sondertasten defür genommen.

4.) Romaji-Input und Deadkey-Unterstützung mittels Präfix-Bäumen

Auf japanischen Tastaturen kann man zwar Hiragana- und Katakana-Zeichen direkt erreichen. Trotzdem geben Japaner ihre Texte wohl lieber im Romaji-Input-Modus ein. Hiragana und Katakana ("Kana") sind Silbenschriften, ein Zeichen bildet also meistens einen Konsonanten und einen Vokal ab (z.B. KA, KI, KU, KE, KO, SA, SI, SU, SE, SO usw.). Nun tippt man einfach die zwei bis drei lateinischen Zeichen ein, die eine solche Silbe beschreiben, und man erhält ein Kana Zeichen zurück. Je nachdem, ob man Shift bzw. Capslock aktiv hat, kommt entweder ein Hiragana- oder ein Katakana-Zeichen. Eine komplette Übersetzungstabelle hierfür findet man am Ende dieses Dokuments:

https://msxjpn.jimdofree.com/%E3%81%8B%E3%81%AA-%E6%97%A5%E6%9C%AC%E8%AA%9E%E5%85%A5%E5%8A%9B/

Da es im Falle vom japanischen Kana eindeutig ist, kann man es über einen Präfix-Baum ("Trie") realisieren, der pro Node bis zu 52 Verzweigungen hat.

Für lateinische Layouts werden dagegen sogenannte Deadkeys benötigt, die aus zwei Zeichen zusammengesetzte Buchstaben erzeugen. Drückt man das erste, passiert erstmal nichts, drückt man das zweite Zeichen, erscheint der eigentliche Buchstabe. Z.B. ` und E erzeugt È, ^ und A erzeugt Â usw. Das ist nötig für Buchstaben mit Diakritika, die nicht direkt auf einer Taste liegen. Auch hierfür wird pro länderspezifischem Tastatur-Layout ein Trie eingesetzt.



In SymbOS werden neue optionale Betriebssystem-Features nach Möglichkeit in Daemons ausgelagert, damit das Kernsystem weiterhin klein und auf Minimal-Systemen lauffähig bleibt. Das betrifft auch die neue Multilingual-Unterstützung, die auf OS-Kern-Seite nur wenig neuen Code benötigt. Das meiste der neuen Fähigkeiten wurde auf Seiten des nachladbaren "Extended Desktop" Moduls implementiert, der nun quasi auch als Language/"i18n"-Daemon arbeitet.

Was jetzt noch fehlt, sind intensive Tests, und auf dem MSX muß die Ausgabe alternativer Zeichensätze beschleunigt werden. Das Betriebssystem, die Systemapplikationen und die wichtigen Standard-Apps sind bisher ins Deutsche, Japanische (danke an Hando!) und Niederländische (danke an EdoZ!) übersetzt worden. Natürlich wären auch französische, spanische, italienische usw. Übersetungen toll. Bei Interesse kann ich gerne die CSV-Dateien zur Verfügung stellen, jede Hilfe ist willkommen!
